## D-018 (2026-11-11, Tier B pilot 2) — overpass.osm.ch mirror is corrupt; empty answers are data poison
The osm.ch Overpass mirror returns HTTP 200 with zero elements and a bogus timestamp for bboxes known to contain data — an empty answer is worse than a loud failure because it looks like "no features". It is removed from the endpoint list (private.coffee + kumi.systems only, 5-attempt backoff). Waterways queries that still fail write an empty layer by design: NHD is the manifest hydrology source. **General rule now encoded in fetchers: a fetched layer that is unexpectedly empty must be treated as suspect, not as ground truth.**

## D-019 (2026-11-11, Tier B pilot 2) — /mnt mount intermittently drops freshly written files
Four files across two builds vanished from `/mnt` after successful writes (siblings written seconds apart survived). `build_county.py` now declares expected payload globs per step (`EXPECT`), verifies after every step, retries the step up to 3×, and calls `os.sync()`. County-file globs are FIPS-specific so a surviving state-level sibling (`eia860_plants_ID.csv`) cannot mask a dropped county file.

*Refinement (2026-11-12, pilot 3):* drops are nondeterministic even with zero concurrent writers — a verified write can vanish within ~8 s and need multiple rewrites before it sticks (observed on `eia860_plants_54047.csv`, a header-only zero-plant CSV). Concurrent writers to the same path make drops near-certain, so: one build at a time per county, fetchers self-heal (verify + rewrite up to 5x before exit), and build_county's EXPECT check remains the final net.

## D-020 (2026-11-11, Tier B pilot 2) — Generalization bugs found by pilot 2 (fixed at the source)
Two pilot-1 constants survived parameterization and were caught only because pilot 2 rendered wrong: (a) the viewer terrain axis projection used hardcoded Thurston reference lon/lat (−96.5, 42.0), shifting Teton's grid +104 km in ENU-y so the camera framed an empty origin; (b) the DEM drape fallback defaulted to 340 m (Thurston elevation), which would bury unplaceable Teton overlays ~1.2 km under the terrain — it now samples the county centroid. **Rule: every per-county constant lives in `county_config.py` or is derived from the payload; a literal number in a build script is a bug.** Viewer template also had a use-before-declaration (`EXAG` referencing `terrMin/terrMax` before the `let`) that crashed the whole scene script; fixed by reordering.

## D-021 (2026-11-11, Tier B pilot 3) — Terrain fallback to 3DEP 1 arc-second via Planetary Computer under egress throttle
Sandbox egress dropped to ~15 KB/s globally on 2026-11-11 evening; TNM whole-tile downloads (~400 MB each) would take ~7 h per tile. **Fallback:** `fetch_terrain.py` probes sustained throughput after 90 s; below 45 KB/s it aborts and window-reads USGS 3DEP 1 arc-second (~30 m) COGs from the Planetary Computer `3dep-seamless` collection — same USGS program, same clip, payload stays at native ~30 m (`dem_<fips>_30m.tif`), source CRS EPSG:4269 treated as 4326 (<2 m datum shift, below the pixel). Partial TNM downloads write to `.part` and are renamed on completion, so an interrupted download can never masquerade as a complete tile. Counties built on the fallback say so in layer meta and the validation sheet. *Invalidated by:* network recovery — a healthy-network rebuild re-fetches at 1/3 arc-second.

## D-022 (2026-11-12, Tier B pilot 4) — Overpass transport: curl GET; Python TLS is reset
Overpass died mid-build again (private.coffee read-timeouts, kumi.systems 504s). Diagnosis: overpass-api.de 406s POST from this sandbox but answers GET with `?data=`; and the egress middlebox resets CPython's TLS handshake (`SSL: UNEXPECTED_EOF_WHILE_READING` in 0.4 s) while `curl` succeeds on the identical query and host (verified with current `timestamp_osm_base`). `fetch_osm.py` `run()` now shells out to `curl -sS -G --data-urlencode` first per endpoint and falls back to urllib; endpoint order is api.de → private.coffee → kumi.systems. ## D-023 (2026-11-12, Tier B pilot 4) — Portal-mount drop escalation: stage in /tmp, settle-and-heal, cursed-path escape
The /mnt drop behavior (D-019) escalated: `nhd_waterbodies_20019.geojson` vanished after FOUR consecutive verified recopies, ~10 s apart each — the portal's async delete queue appears to stick to a path; and `eia860_plants_20019.csv` flip-flopped (present at fetcher start → gone at EXPECT seconds later → present again next attempt), which defeated fetch_grid's early-exit skip (stale `exists()`). ## D-024 (2026-11-12, Tier B pilot 5) — DEM window-clipping bug cropped ALL pilot terrains; coverage now validated
Pilot 5's closeup render showed the terrain mesh ending mid-county. Root cause in `fetch_terrain.py read_windows`: `from_bounds(buffered_bbox, tile_transform)` yields windows that overhang partially-overlapping 1° tiles; rasterio `read(boundless=False)` silently CLIPS such windows, but `window_transform()` was taken from the UNCLIPPED window, so clipped arrays were mis-anchored at the bbox corner and the mosaic collapsed to the last fully-inside tile. Every pilot DEM was cropped where the buffer crosses a tile edge (lat/lon coverage: Thurston 84%/99.7%, Teton 92%/97%, McDowell 100%/93%, Chautauqua 85%/86%, Wilcox 59%/78%). Elevation min/max validation passed throughout — **statistics cannot catch a spatial crop**; render review did. Fix: intersect each window with the tile extent before reading and take the transform from the clipped window. `validate_county.py` gains a "terrain coverage of county polygon ≥99%" check (bbox coverage AND rasterized valid-cell coverage). All five pilot terrains were refetched (full 1/3″ TNM quality — the egress throttle had lifted, so McDowell upgrades from the 30 m D-021 fallback) and all five stages rebuilt. **Rule: any world layer must validate spatial coverage, not just value statistics.**

## D-028 (2026-11-15, national rollout step 1) — OSM from Geofabrik state extracts, clipped locally; Overpass demoted to fallback
Every public Overpass mirror failed for most of 2026-11-11 and 2026-11-12 (D-018, D-022), and a 3,144-county rollout would put roughly 31,000 heavy queries on volunteer-run servers. `fetch_osm.py` now downloads each Geofabrik U.S. state extract once into the shared cache (`$RURALSIM_CACHE`, md5-verified against Geofabrik's `.md5`), picks every extract whose outline touches the county's buffered bbox (so border features are kept), and clips with pyosmium on the build machine. `--state XX` clips every 2024-vintage county of a state in one pass per extract, which is how the national run should call it. Selection uses the same keys and the same unanchored value regexes as the Overpass queries, and the GeoJSON schema is unchanged (`osm_type`, `osm_id`, tags; closed ways are Polygons only when tagged building or area=yes; relations are MultiPolygons of outer rings), so `build_stage.py` and the harness read the output unmodified. Documented difference: Overpass also returns a relation when only a member node is in the bbox; the clipper keeps a relation when an outer member way touches it — the only relations the GeoJSON keeps are matched identically. Features present in two extracts are de-duplicated by OSM type and id. The extract URL, md5 and replication timestamp go into `layers_raw/osm/_meta.json`; `build_stage.py` cites the snapshot for non-pilot counties and leaves the pilots' Overpass label byte-stable. The old fetcher survives unchanged as `fetch_osm_overpass.py` (`fetch_osm.py --source overpass`). Offline semantics test: `tests/test_fetch_osm.py`; pilot parity check: `tools/compare_osm.py <fips>`. **Parity (2026-11-15, Thurston 31173, Iowa + Nebraska extracts):** 9 of 10 themes ≥98.8% shared OSM ids (buildings, schools, healthcare, power, places, food_shops 100%; roads 98.8%; bridges 99.6%). `water` flagged at 8 vs 9: the extra feature is node 14066337249 (`man_made=water_tower`, version 1, created 2026-08-01), inside the bbox and absent from the 2026-11-10 Overpass answer — a mirror omission (cf. D-018), not a clipper error. The first run also exposed that U.S. states cannot be selected from the Geofabrik index by `parent`; they are now matched by extract URL. Remaining four pilots to be checked in the canary run. *Invalidated by:* a parity failure on another pilot that OSM edits between the two retrieval dates do not explain.

## D-030 (2026-11-15, national rollout step 1) — Water systems placed by town or ZIP point; validation counts active systems only
Every pilot flagged "water systems placed" (Thurston 9 of 37, McDowell 21 of 183) for two reasons. The validation denominator counted every SDWIS row, inactive and closed systems included, while the stage only places active ones; and placement matched a single served-town string exactly against OSM place nodes, so multi-town values ("GEORGIANA,PINE APPLE"), annotations ("NORTHFORK (RR NAME NORTH FORK)") and blank town fields never matched. New `place_water_systems.py` (run by `fetch_water.py`) writes `sdwis_locations_<fips>.csv` for active systems: split and normalise the served towns, match OSM places, then Census Gazetteer 2024 places in the same state whose point is inside the county's buffered bbox; for systems with no town, look up city and ZIP once in EPA's WATER_SYSTEM table (contact fields are never stored), and fall back to the Census ZCTA point for the ZIP. A WATER_SYSTEM city or ZIP is a mailing address and is accepted only inside the bbox. Positions are served-town or ZIP points, tagged derived. `build_stage.py` uses the file when present (pilots without it keep the old logic) and `validate_county.py` compares against active systems. Result on the pilots' committed tables, active systems placed: Wilcox 5/6, Teton 21/26, Chautauqua 10/10, Thurston 9/9, McDowell 23/24. The remaining six have no matchable town or ZIP inside the county. Offline tests: `tests/test_climate_water.py`.

Planetary Computer is a maintained service, not a volunteer mirror, and the national CDL raster is several GB per year; revisit if Planetary Computer fails in the canary run. ## D-036 (2026-11-16) — Canary results and the fixes for its seven failure causes
Run 43794676050 built the 57 canary counties (`docs/CANARY.md`): 38 built and published, 19 failed, 0 validation failures among the built (286 pass, 29 flag; 14 counties with no flag). Successful builds took a median 13 min (75th percentile 19, slowest 54: Salem NJ, Esmeralda NV) and publish a median 143 MB (largest 503 MB). Extrapolated to 3,144 counties: about 870 runner-hours and about 530 GB in R2. The 19 failures had seven causes, each fixed here:

1. **Geofabrik refused parallel downloads** (7: CA, CO, IA, NC, OR, SD, VA — "Network is unreachable", 3 attempts each). The plan job now copies each state extract the batch needs into R2 once, serially (`tools/mirror_osm.py`; `osm/<state>-latest.osm.pbf` + Geofabrik's `.md5`, refreshed when older than 7 days, deleted locally after upload), and county jobs read it through the S3 API. Geofabrik stays the fallback, now with 5 attempts and 1–4 min waits. Provenance records where the file came from (`fetched_from`) next to the Geofabrik URL and md5.
2. **County names with spaces broke the EPA URL** (3: Capitol Planning Region CT, DC, New York NY). `fetch_water.py` percent-encodes and retries 5xx answers. Connecticut planning regions will still find no systems by name — SDWIS keeps the 8 legacy counties — and flag; mapping them is open.
3. **An empty EPA answer has no columns** (3: Kent DE, Hawaii HI, Pointe Coupee LA crashed on `primacy_agency_code`). Empty answers are handled.
4. **Out of memory on terrain** (3: San Bernardino CA, Aleutians East AK, Yukon-Koyukuk AK; the runner killed the job before the log could be published). At 1/3 arc-second their mosaics needed 3.6–63 GB per grid. `fetch_terrain.py` now estimates the grid first; above 400 M cells it reads USGS 3DEP 1 arc-second COGs from Planetary Computer, averaged on read when even that is over budget (Yukon-Koyukuk: 3×, ~90 m). The stage mesh is ~160 m, so the viewer loses nothing; the payload file name records the resolution.
5. **Multi-part county boundary** (1: Monroe FL, the Keys). `build_stage.py` draws every part; `boundaries.json` adds `county_parts` (largest part stays in `county` for older viewers) and the viewer frames all parts.
6. **A federal server error failed the county** (1: Cameron LA, NHD waterbodies HTTP 500 ×4, then the settle-and-heal loop reported the file missing). Paged ArcGIS queries are retried with 500- then 125-feature pages; if the source still fails the layer is written empty with a `ruralsim_gap` record, `layers_raw/_source_gaps.json` lists it, validation flags it on the public page, and the next run refetches it. The D-019/D-023 settle-and-heal loop is removed: it guarded against the old sandbox mount, and builds now run on local disk.
7. **TNM product search returned HTTP 500** (1: Garfield WA). Retried 5 times.

Two validation findings, also fixed. **Salem NJ placed 0 of 105 water systems:** New Jersey writes served towns as `PITTSGROVE TWP.-1710`, `LOWER ALLOWAYS CR.-1704`; the matcher now strips the municipal code, expands common abbreviations, and matches Census county subdivisions (townships) as well as places. Re-run on Salem's published tables: 105 of 105 placed (40 OSM place, 65 Census). **Buildings were counted over the buffered bbox, not the county:** Esmeralda NV (21× housing units), Issaquena MS (14×) and Taliaferro GA (5×) were counting neighbouring towns. The check now counts footprints whose representative point lies inside the county polygon. This is stricter on the low side too — Chautauqua KS goes from 802 to 508 footprints (41% → 26% of housing units) — so expect more "below the 80% floor" flags: that is OSM's real rural coverage, and the case for adding Microsoft or Overture building footprints.

Next: re-run only the 19 failed counties, then the first full state. *Invalidated by:* a re-run failure of any of the seven causes.

## D-037 (2026-11-16) — Overture Maps buildings fill OpenStreetMap's rural gaps
Counted inside the county polygon (D-036), OSM building coverage in rural counties is a fraction of the housing stock: Chautauqua KS 26%, Adams IA 19%, Salem NJ 25%. New `tools/fetch_buildings_overture.py` (pipeline step after `fetch_osm.py`) reads the Overture Maps Foundation buildings theme — OSM conflated with Microsoft and Google machine-learned footprints and Esri Community Maps, OSM given first priority, published under ODbL like OSM itself. The release is the one the Overture STAC catalog names as latest (`RURALSIM_OVERTURE_RELEASE` pins another); a bbox index of the release's building files is built once and cached, and DuckDB reads only the GeoParquet files that cover the county, straight from Overture's public S3 bucket (4–18 s per county in testing). RuralSim keeps its own OSM extract as the primary layer and takes from Overture only footprints whose first source is not OSM and whose centre is in the county polygon plus ~1 km — the bbox alone held 215,000 footprints for Salem NJ, most of them in the Wilmington and Philadelphia suburbs. The stage drops any Overture footprint whose centre lies inside an OSM building (an OSM edit newer than the Overture release); heights come from Overture's `height` or `num_floors` when present, else the footprint-class rule. Validation counts both sources the same way and reports them separately; viewers credit "© OpenStreetMap contributors, Overture Maps Foundation" when the layer is present; pilots are unchanged until rebuilt. If Overture is unreachable the layer is written empty and flagged as a source gap (D-036), and the county still builds. Measured on four counties with release 2026-10-21.0, footprints inside the county vs 2020 housing units: Chautauqua KS 26% → 263% (508 OSM + 4,695 Overture), Adams IA 19% → 336%, Salem NJ 25% → 134%, Esmeralda NV 238% → 296% — all now inside the 80%–500% band. Open: footprints are buildings, not homes; the farm counties' 3× includes barns and sheds, which matters where the harness places households on footprints. The next step is to count likely homes (footprint size, land cover) against housing units rather than all buildings. *Invalidated by:* Overture changing the licence of the buildings theme, or a county where the fill duplicates OSM at scale (watch the stage's "already in OSM" count).

## D-038 (2026-11-16) — Stage build speed and a time budget for slow federal layers
In the 19-county rerun (run 43845007357), six jobs ran into GitHub's 5-hour limit. Read from their live logs: five (Washington DC, Capitol Planning Region CT, New York NY, Monroe FL, San Bernardino CA) were inside `build_stage.py`; Yukon-Koyukuk AK was in `fetch_arcgis_layers.py`, where hydro.nationalmap.gov answered HTTP 504 to every NHD request and the retry ladder (4 tries × 3 page sizes × many pages, 300 s timeouts) kept going. Fixes: (1) `demz()` read the DEM with rasterio `sample()` once per point, decompressing a GeoTIFF block on every call; it now reads the DEM into memory once and indexes it. Same values (Chautauqua KS stage byte-identical apart from the build timestamp), 50 s → 13 s on Chautauqua, and the saving grows with road vertices and buildings. (2) The stage draws OSM buildings within ~1 km of the county, as the Overture fill already does; the buffered bbox around Monroe FL reaches Miami, and DC's covers most of its inner suburbs. Roads and other context layers keep the full bbox; validation already counted inside the county. (3) Each ArcGIS layer has a 20-minute budget across all retries and page sizes, with 120 s request timeouts; past it the layer is written empty as a recorded source gap (D-036) and the county still builds. (4) Tribal boundary prim names are sanitised for USD (San Bernardino's "Twenty-Nine Palms" was an ill-formed path).
Follow-up (same day): in the 11-county rerun (run 43912692762) Yukon-Koyukuk AK got through every fetch, including both NHD layers under the new budget, then was killed (exit 143, no log published) right after the cropland step, so in `build_stage.py`. Its DEM is the largest in the country (~194 M cells after the 3× read decimation). `build_stage.py` now reads the stage terrain one needed row at a time instead of loading the full grid (output byte-identical on Chautauqua), and caps the in-memory elevation grid used for draping overlays at ~60 M cells, averaging down for the few counties above it. The workflow sets `PYTHONUNBUFFERED=1` so a job killed for time or memory still shows its last step in the log.

## D-039 (2026-11-16) — One USD prim per layer, not per feature
With the DEM fix (D-038) in, DC, Capitol Planning Region CT, New York NY, Monroe FL and San Bernardino CA still sat in `build_stage.py` past an hour in run 43912692762. Profiling Chautauqua KS with its roads and buildings repeated 10× (40,180 road lines) put 132 of 157 s inside `write_curves`: USD prim creation, one `BasisCurves` prim per road line, growing worse than linearly with the prim count.
